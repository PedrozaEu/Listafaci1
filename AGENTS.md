# AGENTS.md
- Device data is tagged with its owner (`listafacil-owner`: guest or user id); other owners' data is parked in `listafacil-stash-<owner>`, data without a provable owner in the `legacy` stash. Never upload or show data whose owner is not the current account. Why: switching accounts must not move data between accounts.
- `useCloudSync` bumps a generation on every sign-in/out and ignores responses, timers and callbacks from older generations; the list screen renders only once ownership is confirmed (`ready`). Why: late replies from account A must never reach account B.
- Cloud writes to `user_state` use `updated_at` as an optimistic lock. A mismatch with unsent device changes opens a divergence for the user to resolve, never an automatic overwrite or merge; the database trigger archives every previous version into `user_state_history`. Why: no version is ever silently lost.
- Money is stored as integer cents (`priceCents`, `budgetCents`, price history) and parsed/formatted only through `src/lib/money.ts`; `undefined` means not informed and is never summed as zero. Why: avoids float errors and fake free items.
- Data format migrations live in `src/lib/migrations.ts` and run by version for local storage, cloud rows, stashes and backup files alike. Why: every entry point must convert legacy values exactly once.
- Backup, merge and owner helpers live in `src/lib/backup.ts` as pure functions with tests. Why: data-preservation logic must be testable without the UI.
- bun is the only package manager; keep only `bun.lock`. Why: divergent lockfiles produce different installs.
- Route order is the explicit `order` field, computed only by pure helpers in `src/lib/route.ts` (stable tie-break); the view mode is stored per list. Why: inversion, undo and next-purchase must be testable and never depend on array mutation or global settings.
- Quantities, units and line values go only through `src/lib/units.ts`: list items use only `un` (integer) or `kg` (3 decimals) plus free-text `presentation` that never enters math; legacy units are converted only when exact (`simplifyUnit`, idempotent, applied on every read) and otherwise kept unchanged with `unitMigration.status='review'` for the user; frozen purchases keep their original units. BigInt math, one half-up rounding per line. Why: no guessed conversions and no silent data loss.
- Finished purchases are frozen `PurchaseRecord` copies built by `src/lib/purchase.ts`, stored in `purchases` (synced, backed up, merged by id, never edited) and saved idempotently by record id. Why: they are the trusted source for reports and must not change when lists change.
- The PDF report is built in two steps: a pure model in `src/lib/report.ts` (from a frozen purchase or the current cart, never from screen filters) and vector drawing with jsPDF + jspdf-autotable in `src/lib/reportPdf.ts`, loaded on demand; selectable columns, presets, widths/orientation and the device-only last configuration live in pure `src/lib/reportConfig.ts`, and category separators are drawn inside each group's first row so a title never sits alone at a page end. Why: counts, boxes, widths and totals stay testable, the PDF keeps real text, and a personal view preference never touches list data.
- One writer per account: server `legacy_imports.state='active'` means relational storage, else `user_state`. Switch only after the verified idempotent import (checked only against that batch, per entity kind; shared lists are loaded, never compared or imported) (`src/lib/legacyImport.ts`); legacy data is never deleted; rollback writes back with the optimistic lock. Why: two writers overwrite each other.
- Relational changes go through `src/data/opSync.ts`: ops (`src/lib/ops.ts`) and cached state are written in one IndexedDB transaction, removed only after server confirmation, sent only by their creating session, replayed over confirmed state; server dedupes by operation id using server versions. Why: no loss, duplication or cross-account posting offline.
- Service worker only via `src/lib/pwa.ts` (never dev/preview), app shell only, no backend responses, no reload on update. Why: stale previews and reloads mid-edit.
- Live collaboration uses Postgres Changes (RLS-filtered, one channel per open list, `src/data/live.ts`); events only trigger a re-read of the authorized state through `OpSync.refresh`, never replace the outbox; reconnection and a periodic check re-read state to recover missed events and detect revocation. Marks are explicit states: the server keeps the first author and answers `already`/`conflict` instead of toggling; member colors are stored per list by the server. Why: notifications can be lost or outlive access, persisted authorized state cannot.

- Sharing is strictly per list: an invite grants one list with one role resolved from the stored invite (v2 RPCs, token in URL fragment, hashed, single use); guest roles are `editor` and `checker` (marks only), legacy `viewer` links stay in `review` without access until the owner chooses. Access always goes through `list_role` (active links only); the client resolves per-list role only via `resolveListRole` (server owner_id vs session id; unknown sends nothing, delete intent = archive own / leave invited); shared lists never feed the guest's personal purchases/history; copies (`src/lib/listFile.ts`) are always a new private list. Why: a guest must never receive or change any other private data of the owner, and the server alone grants access.
